# Open questions

- Should static-checker errors follow a fixed order? Defer until optimization-loop work: reordering an invalid schedule can change its first reported conflict, but not its rejection.
- How will optimized candidates be proved? Resolve before building the optimization loop.
  - Problem: each certificate is a hand proof tied to one schedule. `Evaluation/Serial.lean` covers only one instruction in flight on lane 0 of the default configuration. The two-lane product pair (8 instructions) already needs ~460 lines, one lemma per cycle. A pipelined multi-lane candidate would cost far more, so proofs would consume the search budget.
  - Proposal: a checker proved sound once. Only the arithmetic-range rule in `Hardware/Machine.lean` depends on input values; every other legality rule does not. One symbolic run, with registers holding polynomials over the inputs plus interval bounds, can therefore check legality, check 16/48-bit fit, and compare each output polynomial with the reference. Prove `check candidate = true → ExecutionSafety ∧ FunctionalCorrectness` once; each new candidate is then certified by `decide`, with no hand proof.
  - Open points: kernel `decide` speed on thousands of instructions (`native_decide` is faster but trusts the compiler, and `scripts/validate.py` forbids it); interval bounds are conservative and may reject some valid rewrites; each workload needs a one-time proof that its reference polynomial matches `reference`; and this sidesteps agent-written proofs, if those are ever the object of study (the brief defers proof-vs-test feedback).
