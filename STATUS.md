## Decisions

- `PLAN.md` is the implementation contract. Preserve its hardware semantics and scope.
- Implement only the assigned milestone; leave a factual handoff before stopping.
- Prefer simple Lean structures, functions, and reusable proofs. No optimization strategies or LLM integration.
- A successful build or tested numerical result is not a substitute for the required all-input correctness and execution-safety proofs.
- Workers propose completion; the coordinator marks a milestone verified after inspecting its artifacts and checks.
- Staging correction after Milestone 3: Milestone 4 constructs and structurally validates the tiny multiply program; its execution gate is explicitly assigned to Milestone 5, which implements the simulator. No hardware rule or final deliverable changed.
- Milestone 1 pins the already installed `leanprover/lean4:v4.35.0` (Lean commit `eb6cafb7290e8bd5f2937522d8d804f58f02bafc`, bundled Lake `5.0.0-src+eb6cafb`). No toolchain download or external dependency was needed. Mathlib is deferred until it materially simplifies a later proof.
- Initial identifiers are `arty-model-v1`, `candidate-v1`, `latency-v1`, and `energy-proxy-v1`; the specified coefficient set is separately named `energy-coefficients-v1`. These are contract identifiers, not claims that their later implementations exist yet. Milestone 3 records workload versions with their specifications: `matvec-16x16-signed16-v1` and `matmul-16x16-signed16-v1`.
- The package/executable uses the simple identifier `optimal_computation`. An initial hyphenated target built, but `lake test` did not resolve it as a driver; renaming it resolved that failure. No machine-contract correction was necessary.
- Milestone 2 keeps raw `Config` separate from proof-bearing `ValidConfig`. Validation identifies unsupported lanes or banks (lanes first if both fail). Hardware mappings and resource reports require the latter, so an unsupported configuration cannot receive an accepted allocation report.
- Fixed capacities are shared hardware constants. `Address` and `BankLocation` use bounded `Fin` coordinates; `bankAccessesFit` checks per-bank port capacity only. Full same-address, access-kind, and schedule legality remain for Milestone 5.
- Resource reports include pending-instruction slot capacity separately from writable architectural bits. Control, connection, pipeline, and total LUT/flip-flop area use `Option LogicArea = none` for uncalibrated, never zero. No model semantics or version changes were necessary.

- Milestone 3 uses exact `Int` ranges and proof-bearing `Signed16`/`Signed48` values. Checked operations reject invalid operand widths before testing the exact result; errors retain the field, width, and value. `checkedMac a b accumulator` has a documented left/right/accumulator/result check order.
- Numeric `Slot64` stores an actual `BitVec 64` with a canonicality proof. Raw noncanonical patterns are rejected. Encoding is only performed after a signed 48-bit range proof; the bit-vector constructor therefore cannot cause numeric wrapping. Round trips and equivalence to 48-to-64-bit sign extension are proved.
- The workload interface carries its identifier, input type, input predicate, output type, and pure reference. Matrix entries remain runtime integer inputs. Both references use a recursive increasing-index `dotPrefix`, with reusable bounds for every prefix up to 16 and exact next-prefix checked-MAC success. No addresses enter the reference functions.
- No dependency or machine-contract correction was needed. The Lean standard library supplies integer arithmetic, bit vectors, and the proof tools. A finite-predicate instance is instantiated explicitly to avoid recursive typeclass search during input validation.

- Milestone 4 separates natural-number raw data from bounded instructions, nonzero destinations, proof-bearing layouts, and `Candidate shape`. Exactly five generic primitives are shared by raw and bounded syntax. A scheduled instruction has one bounded lane, so every operand is local to that lane. No runtime values or initialization overrides occur in the candidate format.
- A layout is three finite lists: input/output positions are logical scalar indices, while scratch explicitly reserves additional slots. One global `Nodup` proof enforces internal injectivity and pairwise disjointness. All entries use the existing bounded `Address` type. Validated loads name declared slots; validated stores name only outputs or scratch.
- `validateCandidate` receives a trusted expected `Workloads.Shape`; it checks the raw workload ID and exact input/output counts. `MatVec.shape` and `MatMul.shape` expose their existing specifications' IDs and counts, while hardware and candidate modules import no concrete workload registry. Later semantic verification must also bind the specification and scalar encoding; matching an ID/shape is not a correctness proof.
- Validation preserves schedule order and explicit issue cycles. It allows a destination to be its own source, source `r0`, and structurally declared output/scratch loads. Readiness, initialization, issue/writeback collisions, memory contention, numeric execution, pending capacity, and completion remain Milestone 5 obligations. No initial runtime state or simulator was added.
- Stable fixture `tiny-multiply-v1` uses workload `scalar-multiply-signed16-v1`, configuration `(1, 1)`, inputs at slots 0/1, output at slot 2, and issue cycles 0/1/2/5 for load/load/multiply/store. Its inputs remain runtime values. A kernel-checked theorem proves its structural acceptance, not its execution or all-input correctness. No machine/version change was required.

- Milestone 5 uses one pure `Hardware.step` for execution: commit due effects, canonicalize/check the simultaneous batch, prepare every payload from the same post-commit state, then enqueue. Loads/stores complete at `t+1`, arithmetic at `t+3`. Diagnostics and traces use ascending lane order; duplicate issues are rejected before inspecting per-instruction operands. Bank and same-address conflicts are checked across the whole batch.
- State uses fixed-size vectors for registers and 4,096 canonical memory slots, plus a vector of per-lane pending-effect lists. Each successful reservation checks the three-entry capacity, pending-register hazards, and future register writeback conflicts. **The raw `State` type itself does not prove pending-list capacity or reachability.** Milestone 6's all-input safety work must establish the reachable-state capacity, issue, and writeback invariants explicitly; the direct synthetic-state capacity test is not such a proof.
- Inputs alone are installed by `initialState`; zero-register reads return zero, and writable registers, outputs, and scratch are `none`. The scalar adapter checks exact count and signed48 transport width. Workload-specific allowed-input checks and proof binding remain Milestone 6 responsibilities. No transition or execution function calls a workload reference.
- The runner sorts the schedule once and consumes each boundary's prefix, avoiding a full-schedule scan on every cycle. Its explicit budget counts processed boundaries, including boundary zero. A six-cycle run needs seven boundaries. An empty zero-output program finishes at cycle zero with zero budget. Resource exhaustion is a separate inconclusive result with next-boundary/issued/remaining/pending counts.
- Execution records contain versions/identifiers, output scalars, elapsed cycles, resource/storage reports, schedule size, and event-derived counters. Operand reads (including repeated r0 operands), memory requests, and operation kinds count at issue; register writes count at commit. MAC is one MAC event. Lane activity records issued/completed counts and occupied intervals `[t,t+1)` after issue. Initialization generates no events. Trace suppression changes no counters, outputs, or timing. No scoring or verification label is attached to concrete-run success.
- Public vector-update/read lemmas and `run_step`/`run_finished` expose reductions of the actual executable semantics for later compositional proofs. No alternative proof-only simulator, new dependency, model change, or version change was introduced.

- Milestone 6 introduces workload-owned `ScalarAdapter` values with input/output left inverses, exact scalar counts, and allowed-input transport-width proofs. Tiny multiplication and both matrix specifications have codecs; matrix inputs/outputs use row-major order. Output decoding receives only output scalars, never the input or reference function. The matrix codecs contain no matrix candidate or baseline.
- `VerifiedCandidate adapter` carries the exact typed candidate, a sufficient boundary budget, and separate `ExecutionSafety` and `FunctionalCorrectness` fields. Both quantify over every allowed logical input and refer to the existing `executeValues`, hence the actual `run` and `Hardware.step`. Safety is successful finite execution with drained pipelines/written outputs; all numeric intermediates pass the existing range checks. Correctness compares every returned output scalar to the specification's reference through the adapter.
- The tiny theorem `Examples.TinyMultiply.execution_correct` quantifies over arbitrary `Int a b` with signed16 proofs. Transparent reductions of the real machine plus the existing checked-multiply and canonical-slot lemmas prove a successful seven-boundary run, output `[a*b]`, and elapsed cycles 6. `TinyCertificate.verified` binds that theorem to the scalar-multiplication specification and exact artifact. No fixture enumeration, reference-only executor, or candidate-supplied correctness Boolean occurs.
- `Hardware.Invariants` proves generic preservation of pending length at most three per lane by successful `commit`, reservation/prepare, enqueue, and `step`. Initialization is bounded; `Reachable` is defined by actual successful machine steps; `run_finished_reachable` connects finished runs to this relation. Successful batch checks imply issue/bank/address predicates. Successful commits imply at most one due register write per lane. These are generic theorems, distinct from tiny-only all-input functional correctness. Raw hand-built State lists remain unbounded; signed48 registers and canonical memory/pending payloads remain bounded by their types.
- `inspect` reuses structural validation and adds a proved exact serialization binding. `checkStatic` reuses `checkBatch` at every nonempty scheduled boundary, with a soundness theorem for input-independent issue, bank-port, and address restrictions. It does not claim to prove readiness, initialization, arithmetic or termination; those remain execution/certificate obligations.
- Registered evaluation checks the workload input domain and complete candidate equality, including configuration, layout, schedule and versions. At the end of Milestone 6 the registry contained only the tiny certificate. The accepted path fixes trace capture to `false`, exactly matching its theorem. Arbitrary trace-enabled executions remain simulations. Actual-run fuel monotonicity justifies successful evaluations at a smaller budget; exhaustion remains inconclusive and retains actual progress details.
- Unified failures distinguish invalid input, inadmissible configuration, malformed layout/artifact/instruction, illegal schedule, arithmetic failure, incomplete output, and unverified candidate. Simulation results have a separate constructor from verified results. No hardware semantics, numerical rule, version, dependency, or executable transition was changed. Tiny address/register/lane constants were made public to support the proof module; their values are unchanged.

- Milestone 7 adds `matvec-naive-v1`: default `(8, 8)`, lane zero only, r1/r2 operands and r3 accumulator, matrix/vector/output slots 0–255/256–271/272–287, no scratch. Each row resets r3 using `add r3,r0,r0`, then explicitly loads matrix and vector operands and MACs in increasing column order before storing its output. There is no cross-row reuse or parallel issue.
- Every primitive waits through its completion boundary; the next instruction issues one boundary later. A row consumes `4 + 16*(2+2+4) + 2 = 134` boundaries. Sixteen rows process 2,144 boundaries and finish at elapsed cycle 2,143. The frozen program has 800 instructions, 512 loads, 16 stores, 16 adds, 256 MACs, 816 register reads, 784 register writes, 528 bank accesses and 1,344 lane-zero active intervals. These deliberate conservative waits and all formulas are documented in `docs/results/README.md`.
- `Evaluation.Serial` proves primitive issue/wait/commit facts for the existing default configuration and composes them through the actual `run` with an arbitrary later queue. Its `Executes` proposition consists of actual successful `prepare` facts, not a second executor. `SerialDot.executes_prefix` proves arbitrary signed16 dot prefixes at arbitrary operand addresses, preserving all memory. `MatVecProof` composes row execution, proves the actual initializer's input mapping, binds the sorted schedule, and proves all output slots written with the reference values.
- `MatVecNaive.execution_correct` quantifies over every allowed matrix/vector input and proves `executeValues candidate (adapter.encode x hx) 2144 false` succeeds with all sixteen exact outputs and cycle count 2,143. `MatVecNaive.verified` supplies separate safety/correctness fields. The certificate covers the primary default artifact; all 16 configuration variants are additional conformance simulations. Runtime execution never calls a reference or expected-output function.
- The registry retains tiny behavior and adds matrix-vector lookup through complete candidate equality, including configuration, layout, schedule and versions. `selectCandidate` selects either stable identifier; `registered_sound` covers the two registered cases. All accepted evaluation remains on the trace-disabled proof path. Altered schedules/configurations or renamed artifacts receive no certificate.
- The new proof modules use Lean's elaboration transparency option to resolve definitionally equal dependent state/adapter types; this changes elaboration, not trusted semantics or kernel checking. No new dependencies, hardware rules, arithmetic rules, versions, objectives, matrix-matrix program, optimization/search strategy or AI loop were introduced.
